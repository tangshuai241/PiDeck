# 需求对齐交互整体评估

状态：用户已试用对齐流程，反馈暂未发现功能问题；已指出并修整模式退出 X 的视觉问题，并授权验收后提交、更新现有 PR。本文保留改造前的问题证据，并记录现行实现；完整真实成品任务和安装包仍未正式验证。

## 结论

当前问题不是缺少动效，而是状态含义错误、确认语义不清、聊天与卡片重复展示。先统一交互，再调整外观。不得用放宽确认条件解决灰色按钮。

本轮按用户批准的“单聊天流 + 最终确认单”方案改造。此前未提交的相关改动已纳入本次收口；完成自动化验证不等于用户已经验收。

## 改造前已确认的问题

| 问题 | 改造前实现 | 后果 |
|---|---|---|
| 空输入显示正在处理 | `AlignmentCard.cardPhase` 对没有 state 的情况返回 working；working 无条件旋转 | 用户没有发消息，也看到假进度 |
| 有草稿就宣称完成 | idle 时 clarifying + brief 被映射成 ready；横幅固定使用 readyTitle | 未决问题仍存在时，横幅说完成，按钮却禁止执行 |
| 展示和审批使用不同判据 | 横幅依据 cardPhase；按钮依据 canApproveAlignment + busy + pending | 用户无法从界面判断何时能执行 |
| 同时出现两套进度 | 主聊天有运行反馈；对齐卡片另有旋转和呼吸动画 | 两个区域争夺注意力 |
| 同时出现两份正文 | AI 在聊天中总结要求；输入框上方再显示完整要求 | 用户不知道以哪份内容为准 |
| 用投递成功替代确认成功 | hook 在 sendPrompt 返回 accepted 后切换 mode | accepted 不保证扩展已经批准，界面可能提前报告成功 |
| 测试固化错误语义 | e2e 对 questions=1 同时要求 data-phase=ready 和按钮 disabled | 测试通过不能证明交互一致 |

以上证据来自改造前的工作树，不用历史 transcript 覆盖现行代码。

会话记录中的 aborted 只能证明回合中断。它不能单独证明点击“修改要求”导致中断，也不能用消息时间戳推定完整生成耗时。此前以此归因的说明不作为本次方案依据。

## 两个动作，各管一件事

- 发送消息：提交目标、回答问题或修改说明。AI 可以只读检查材料、更新要求，不开始制作。
- 确认并开始执行：用户批准当前可见的要求版本。pi 记录批准后开始制作；原有工具权限和安全审批仍有效。

确认不是再次发送消息，不是保存草稿，也不是对生成成果的验收。

现行按钮名称为“确认要求，开始执行”。

## 融入方式比较

| 方式 | 好处 | 代价 | 判断 |
|---|---|---|---|
| 保留输入框上方卡片，只在可确认时出现 | 改动较少，沿用现有容器 | 最终确认仍处在另一个视觉区域 | 可作为低成本备选，但不得保留第二套进度 |
| 在聊天流末尾显示最终确认单 | 提问、回答、更新反馈、最终确认都在同一区域 | 要处理历史确认单、滚动、多会话和旧版本失效 | 推荐，解决单一关注点问题 |
| 单独抽屉或表单 | 适合直接编辑多字段 | 新增操作空间和数据同步负担 | 当前不采用，不能用更多 UI 弥补状态错误 |

推荐“单聊天流 + 最终确认单”，不增加第二个输入框、常驻侧栏或新的弹窗。

## 推荐流程

### 未开始

选择需求对齐，只改变输入框的模式和说明。不展示旋转、处理提示或要求正文。用户可以正常输入目标。

### 已发送，处理中

输入发送后立即显示一次静态反馈，例如“修改已发送，正在重新整理要求”。真正运行中的动效复用主聊天现有动效，不另加转圈。

旧确认单立即从可执行位置撤下，改为静态发送或处理提示。若消息仅排队，显示“等待处理”，不能说更新完成。投递失败时说明失败并保留输入，不让用户无限等待。

### 等待用户回答

AI 回复结束，但仍有未决事项时，显示“还需要你回答 2 个问题”。这不是运行中，不显示旋转，也不显示整理完成。

问题只在聊天中展示一次。不要把草稿字段作为完整要求再次展示。AI 不反复询问用户已经决定的内容。

### 可确认

仅当完整要求有效、没有未决事项、当前 runtime 空闲、没有待处理输入且没有控制操作在途时，展示最终确认单：

- 标题：“需求整理完成，请确认”。
- 内容：当前目标、范围、成品、保留项、完成标准。
- 按钮：“确认要求，开始执行”，此时必须可点。
- 修改方式：继续在同一个输入框发送修改说明。

最终确认单是唯一完整摘要。AI 聊天正文只说明“要求已整理，请查看确认单”，不重复整份正文。

### 批准、执行和异常

点击确认后显示“正在确认”，锁定重复点击。收到扩展的权威 approved 状态后，显示“已确认，开始执行”。不能仅凭 sendPrompt.accepted 报告批准成功。

批准失败、运行时换代、更新未发布、回合停止或出错，都必须显示真实原因和可采取的动作。不得自动批准旧要求，不得自动重试制作。用户的修改消息已在会话中时，不要求用户凭空重打一遍。

执行中的动效只用主聊天现有反馈。旧要求仍保存在 pi 会话中；界面不把历史批准恢复成正在执行，也不提供过期批准按钮。

## 必须保留的能力

| 现有能力 | 新交互如何保留 |
|---|---|
| pi 维护对齐状态和会话读写 | UI 只投影状态，不自己批准，不新增模型调用通道 |
| 对齐阶段只读 | 不扩大工具白名单、不通过 UI 绕过权限 |
| 精确版本确认 | 保留 briefId + revision 校验 |
| runtime 身份校验 | 保留 sessionId + agentId + runtimeGeneration |
| 历史恢复和异常降级 | 旧批准不自动执行；损坏状态不复活旧确认单 |
| 普通聊天、plan、goal 和关闭桥 | 原行为保持；确认单不依赖 GUI 桥开启 |
| 多会话和主题 | 按 session 订阅；沿用现有组件及语义 token |

## 实施顺序

1. 先写失败测试复现空输入假进度、完成与禁用矛盾、发送后的旧确认单仍可批准。
2. 抽出纯展示策略。一个策略同时决定状态标题、正文可见性、动效 owner、按钮可用性及失败原因。
3. 在现有标准 RPC 投影链上核对输入投递、排队、运行结束和权威批准的映射。UI 信号不足时在现有契约内补齐，不引入第二条通道。
4. 迁移最终确认单到聊天流，删除原卡片的重复进度和正文。App.tsx 只装配，不承载新业务逻辑。
5. 用真实生产 hook 和 mock IPC 验证连续状态流转。静态 fixture 保留亮暗主题验证，但不能代替流程测试。

## 已实施的状态边界

- `alignmentPresentation.ts` 是完成标题和确认按钮的共同判据。没有输入时隐藏；未决问题、排队、发送、运行、失败和未更新草稿都不能冒充完成。
- 最终确认单仅挂在 `SessionMessageTimeline` 的聊天流中。输入框保留模式选择，不再挂第二份正文或进度。
- 左侧退出 X 与模式选择器共用28px高的容器，X 的可点区域为24px、图标为12px。覆盖 Select 的条件高度并取消独立灰块、阴影；亮暗主题和360/640px底栏均核对。原来的窄栏图标化、隐藏菜单时退出兜底及禁用规则保留。
- `alignmentSubmissionAtomFamily` 在普通发送和队列投递前记录本会话的提交屏障。模型尚未发布新要求时，旧确认单不能执行。队列计数同步阻止确认，不影响其他会话。
- 权威快照新增兼容旧数据的可选 `briefRevision` 和 `lastStopReason`。输入使状态版本失效，但不改写旧字段的发布版本；只有 `alignment_brief` 发布才更新 `briefRevision`。因此恢复历史时也能分辨保留的旧问题与真正新发布的问题。停止原因只描述结果，不推断由谁中断。
- 确认等待同一 runtime、同一 `briefId + revision` 的 `approved/complete`。等待有超时，订阅和定时器配对释放。RPC accepted 仅表示投递，不表示批准。
- 失败提示绑定 runtime 和要求版本，不污染新版本。继续整理走原有只读输入通道，使用会话已有回答，不自动执行；迟到回复不能结算新 runtime 的发送状态。
- 模型指令要求纳入最新修改、移除已回答的问题、避免重复完整摘要，并引导使用桌面确认按钮。指令不能保证每个供应商都会遵守，因此仍保留真实模型验收。

## 验收门禁

- 选模式但未输入：零处理中提示、零旋转、零最终确认单。
- 首次发送及再次修改：立即有接收反馈；整个页面仅一处运行反馈。
- AI 结束但有问题：明确等待回答；不显示完成，不显示无限转圈。
- AI 结束且要求完整：最终确认单出现，确认按钮可点。
- 显示“需求整理完成，请确认”与确认按钮可点必须使用同一判据。
- 修改发出后：旧版本不能批准；更新完成后出现新版本确认单，不只静默替换正文。
- 停止、错误、投递失败及未发布新要求：真实提示，有继续路径，不能保留假完成或假处理中。
- 确认后：只执行一次，收到 approved 才报告成功；旧 runtime/旧 revision 不能执行。
- 历史恢复、两会话切换、亮暗主题、关闭 GUI 桥均验证。
- 类型检查、相关单测、连续交互 E2E 全绿后，才能邀请用户再次验收。不以“静态截图通过”替代交互验收。
