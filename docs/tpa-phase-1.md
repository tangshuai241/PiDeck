# TPA 第一阶段改进计划

状态：部分实施。会话内需求对齐首版源码已落地；完整第一阶段尚未完成。日期：2026-10-11。

本阶段验证桌面上的个人助理体验：普通事情直接聊，重要工作由用户选择开启对齐，执行进度与成果回到同一段对话。

长期方向见 [长期改进路线](tpa-roadmap.md)。以下对话均为设计场景示例，不代表全部已实现。

当前先保留现有界面，在输入区加入可选的会话内需求对齐。首版支持澄清、修改要求和明确确认，再交给当前 Pi 会话按既有权限执行。它尚未接入 Workbench 任务、成果与改稿服务。使用方式、技术边界和验证范围见 [需求对齐首版](tpa-alignment-v1.md)。

## 现有基础与本次增量

PiDeck 已有内置 Chat 项目、会话历史、模型与工具配置、MCP，以及 Pi 扩展的 GUI 桥。本阶段沿用这些能力，改进入口和助理行为，并在对话中串接要求、执行与成果。

现有 Workbench MCP 已验证工具发现和认证读取。对齐、出稿、改稿的完整集成仍待联调；本机 MCP 也不是完整的云端助理代理。

## 本阶段改什么

| 改进 | 具体变化 |
| --- | --- |
| 明确的助理入口 | 复用内置 Chat，优先呈现自然对话和当前工作；项目开发入口继续保留 |
| 稳定的助理行为 | 日常聊天自然回应；常规整理、分析和小任务按用户要求直接推进，不默认进入完整对齐 |
| 用户选择对齐 | 输入区提供明确的对齐入口，也识别用户“先对齐要求”等明确指令；开启状态绑定本次工作，工作结束后回到普通对话 |
| 同一对话中的要求与方案 | 展示读到的材料摘要、已有要求、待澄清项和方案；用户能修改，再决定执行 |
| Workbench 执行与改稿 | 在后台关联任务，复用原服务的方案、审批、执行和改稿；进度、成果与错误回到当前对话 |
| 可判断的状态 | 区分方案待确认、执行中、已出稿、失败和中断等状态；重开后查询原任务，保留成果版本 |

完整对齐与动作授权分别处理。关闭对齐仍保留必要澄清和原有审批；用户已明确授权的动作，也不因新界面而重复询问无关问题。提交执行前，应满足现有服务要求的必需信息与审批条件。

## 改进后的使用场景

### 1. 下班后随便聊几句

你说：“今天有点累，不想安排太多事情，陪我理理思路。”

助理直接围绕当下状态回应。界面不要求新建任务、选工作流或填写目标。第一阶段的回复依据当前会话和明确提供的背景，不宣称已经接通长期记忆，也不暗中把闲聊写成日记或待办。

### 2. 普通小事直接完成

你粘贴一段会议记录，说：“整理成五条行动项，再给我一份 Markdown 文件。”

助理按要求整理，必要信息不足时简短澄清。它在对话中给出内容与可打开的文件，不展开完整对齐流程，也不自动将行动项登记成待办。

这一场景主要验证：现有工具能力能否在个人助理入口里顺畅使用。

### 3. 重要文稿主动开启对齐

你提供参考材料，说：“根据这些资料写施工总结，先把要求和方案对齐。”也可以点击对齐入口。

助理先读取或转换材料，展示实际读到的内容摘要；读不到的文件直接说明。随后在对话中整理范围、口径、缺项与方案，你可以修改，例如“只写桥面系部分，未核实的数据先留待补”。

确认后，执行器通过原有审批与执行校验开始工作。你在这段对话里查看进度并打开成果，无需先去任务页填表。上传成功不等于材料已经读完，出稿也不等于用户已经验收。

### 4. 做到一半再决定对齐

你原本只要求简单整理，看到草稿后说：“这个要正式使用，还是先对齐一下要求。”

助理以当前对话、已有材料和草稿为起点开启对齐，你不必重新交代。界面明确显示本次工作进入对齐流程；下一件普通小事仍按普通对话处理。

AI 认为需要对齐时，可先提出这一选项，等用户选择后再开启。

### 5. 在成果下面直接改稿

你打开成果后说：“第二节太泛，结合参考材料重写，第一节保留。”

反馈关联到当前成果所属的任务和版本，继续原有改稿链路。完成后展示新版本，同时保留旧稿和本次要求。若有多个任务或版本，先明确修改对象。

你能分清“已经出稿”和“我认可这版成果”，不会因为文件存在就自动标成验收通过。

### 6. 关闭窗口或服务暂时不可用

关闭 TPA 再打开时，已有工作能恢复显示，并查询原任务的最新状态。后台仍在运行的任务不会再次启动；实际中断的任务明确显示中断或待核实结果。

如果 Workbench 服务不可用，界面保留本次要求，并给出重连或重新尝试入口。它不会把尚未提交的工作显示成已经排队，也不会宣称已经完成。

## 实现范围

- 会话内对齐首版沿用 Pi 的标准 RPC、原生会话与工具机制，在 PiDeck 现有输入区呈现要求卡，不依赖 GUI 桥。Workbench 适配层仍待实施。
- Workbench 继续作为其任务事实源和唯一写入服务；TPA 保存会话与任务的关联，不直接修改任务档案。接入前确认接口访问的是当前权威任务服务。
- 先用隔离材料和数据验证材料读取、审批、执行、取消与改稿。需要其他项目新增接口时，单独列为依赖，不在本阶段擅自改其源码。
- TPA 试用使用独立应用标识、数据目录和更新配置，避免与原版混用。真实聊天、认证和运行数据不进入源码仓库。

完整长期记忆、日记管理、微信接入、离线执行队列和新增主动定时留到后续阶段。第一阶段不承诺电脑关闭后仍能继续所有本机工作。

## 实施顺序

1. 保留现有界面和普通对话，先加入可选的会话内需求对齐与要求卡。首版源码和自动化测试已落地，真实模型与完整桌面联调仍待验证。
2. 接通 Workbench 工具与任务关联，用隔离样例验证执行和成果展示。
3. 将已确认要求关联到 Workbench 任务与方案版本，复用原服务的审批、执行和幂等约束。
4. 完成成果改稿、任务状态恢复、取消与失败处理，验证整段使用过程。

## 第一阶段完成标准

- 普通聊天和小任务不强制经过完整对齐。
- 用户可以在同一段对话中开启对齐、修改要求、确认执行并取得成果。
- 普通工作中途可以升级为对齐流程，已有内容继续使用。
- 改稿有明确的任务与版本归属，旧稿保留。
- 服务离线、失败或重启后，界面反映真实状态，不自动重放结果不确定的动作。

达到这些标准后，再判断它是否让人愿意持续使用，并据此调整第二阶段范围。
