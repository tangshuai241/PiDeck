# TPA 按需记忆、人格与原话回传实施方案

日期：2026-10-14。文档版本：3。
状态：N00 到 N12 已完成工程与独立环境验收。N13 已完成源码提交授权、云端实现提交和正式契约绑定；桌面实现随本文提交，发布包、正式发布与日常入口验收尚未完成。N14 尚未开始。默认关闭，未改正式服务或用户日常配置。证据汇总见[工程验收记录](tpa-cloud-memory-acceptance-v1.md)。

## 1. 目标与完成后的场景

本方案让电脑端与云端助理使用同一份个人资料，同时保留本地项目工作的正常行为。

- 普通计算、改稿和文件工作按当前材料执行，不因每轮自动检索个人记忆而等待。
- 问到个人背景、过去决定或项目历史时，当前 Pi 模型调用工具查资料，再按需要读取原话。
- 本地用户输入和助手可见回答进入后台待传队列。云端保存原话，不再生成一次回答。
- 后台从原话中整理长期资料。每条资料能回查来源，问句、决定和助手推断分别标记。
- 云端维护已确认的人格版本。本地保存已确认版本的缓存，回答不以下载人格为前提。

完成不等于两个入口逐字回答相同。模型、当前会话与任务材料仍会影响回答；共同的是人格发布来源、长期个人资料和可追溯来源。离线入口可暂时使用旧的已确认人格版本，恢复连接后更新。

## 3. 三条运行链路

### 3.1 按需读取

当前问题 → Pi 模型决定是否需要历史 → 搜索工具返回候选预览与来源。

模型指定记录读取详情／原话 → 工具结果进入 Pi 正常上下文 → 当前模型继续回答。

没有调用记忆工具时，不新增记忆正文，也不发起召回请求。已有工具结果仍遵循 Pi 正常会话与压缩行为，不能将“本轮没查”描述成“模型输入没有历史”。

### 3.2 本地原话回传

Pi 原生会话保存 → 采集新增可见消息及修订事件 → 本地持久待传队列。

后台上传 → 云端核验并保存 → 返回可核对回执 → 本地标记已同步。

回答不以上传完成为前提。断网和重启后，未确认记录继续保留。上传原话不调用聊天模型。

### 3.3 后台整理与人格更新

云端原话归档 → 后台整理长期信息 → 保留来源及有效状态 → 写入 Hindsight → 两端按需查询。已确认人格发生变更 → 云端生成新 revision → 本地后台刷新缓存 → 下一用户回合使用新版本。

后台整理若使用模型，单独记录用量和耗时。原话保存、记忆整理和人格更新分别记录状态，不能用一次“上传成功”代表全部完成。

## 4. 实现约束与数据契约

### 4.1 职责归属

| 模块 | 职责 | 边界 |
|---|---|---|
| Pi 扩展 | 工具、人格注入、原生会话采集、待传队列与后台发送 | 不改写运行中的原生会话文件；通过 Pi 公开 API 工作 |
| TPA 主进程 | 连接设置、受保护的认证配置、扩展启动和状态适配 | 与 Pi 的运行时通信仍走 stdio JSON-RPC，不增加文件轮询桥或通用 SDK 桥 |
| 云端领域模块 | 账号校验、检索、来源回读、在线原话导入、后台整理 | HTTP handler 只做校验与适配；归档不进入回答／任务执行队列 |
| Hindsight | 长期记忆的保留、查询和有效状态 | 不作为每次回答的第二个聊天模型 |

首版由 Pi 扩展拥有采集、队列和发送，避免以共享文件建立第二条 Pi／TPA 运行时通信通道。所有 Pi 进程退出时，持久队列保留；下一次 Pi 启动恢复发送。若以后要求“TPA 开着但没有 Pi 运行时也持续上传”，应另定架构，不能在本期暗中增加常驻服务。

连接配置属于启动／设置数据。同步状态通过正常 RPC 的原生扩展消息或命令呈现。前台显示已核实状态，不能把旧回执当作实时队列已清空。

### 4.2 检索与大小

- 两级读取工具为 `search_memory` 和 `get_memory_source`。前者搜索候选预览，后者按来源引用读取独立原话库中的记录。来源读取重新校验账号权限，不因模型提供编号就放行。
- 搜索不固定取三条。正文预算控制返回量，条数随记录长度变化。
- 初始正文预算拟为 500 token；来源、预览标记和包装另占用量，不承诺最终模型输入严格等于该预算。
- 搜索返回稳定编号、预览、来源、时间、作用范围和完整性标记；不额外调用聊天模型写候选摘要。
- 详情按指定编号读取。长原话分段，返回总大小、片段位置、原文哈希和继续读取位置。
- 超出传输大小时分页或明确报错，不静默把半条原话标成完整记录。接口字节上界是资源约束，不是召回耗时截止期限。
- 已经取得的资料直接使用。模型需要新资料时再调用工具，不以隐式规则在每轮预先检索。

### 4.3 原话与队列

来源身份至少包含已认证账号、云端实例、设备、Pi 原生会话和来源条目编号。宿主 `SessionRecord.id` 可作关联，不以易变的 agentId 或进程号替代原话身份。

原话记录保留角色、原始可见文本块、发生时间、项目标签、父条目与分支关系。用户输入和助手输出分别保存；取消或错误后的部分回答明确标为未完成。

去重键由来源身份与版本组成。内容哈希按冻结的规范化契约计算，不能把待传状态、上传时间或云端序号纳入原文身份。原文回读应与来源可见文本逐字一致。

同编号、同内容重传返回同一记录；同编号、异内容返回冲突。合法编辑、删除和分支切换发送新的修订／可见性事件，云端默认视图遵循当前分支，原始记录仍保留。界面隐藏不等于远端彻底删除原件。

默认采集提案是用户与助手的可见对话。工具结果、思考过程、系统提示和自动读取的文件正文不随该入口回传；附件先保存引用。用户直接粘贴进消息的材料属于原话文本。

待传状态区分未发送、已发但结果未知、已确认、认证待恢复和内容冲突。只有可核对的云端落盘回执才允许标记已同步。未知结果先查回执，不盲目创建新消息编号。

回执应绑定账号、云端实例、来源编号、修订和内容哈希。“请求已受理”不能代替落盘确认。确认后可清除待传副本，但本地原生会话和云端原话仍保留。原话已保存、记忆已提取和索引可检索分别记录；整理失败不退回原话未上传状态。

网络暂时失败可重试；认证失效时暂停发送，恢复认证后继续。内容冲突、存储损坏和额度不足应保留记录并显示原因，不能无条件重试。

### 4.4 账号、项目与人格

云端按认证身份确定账号，不接受正文指定其他账号。队列和缓存绑定账号及云端实例；切账号后不能把旧账号待传内容发给新账号。

项目标签只用于资料分组，不创建任务、派发执行或增加另一套任务权限。个人原话、项目知识和外部案例应能区分。

项目聊天是否归档与其中内容是否成为个人长期资料，是两个决定。归档不自动把代码、错误日志和助手提出的方案写成个人资料。项目决定和经验保留项目作用范围；用户明确表达的个人偏好才按来源与确认状态参与个人资料整理。

云端供应商模型凭据与用户会话认证分别管理。认证文件不写入源码、测试报告或普通日志；用户凭据在连接界面输入，不在聊天中收集。

人格保留原稿、已确认注入稿、启用状态和 revision。本地使用已确认缓存；后台检查更新，当前回合保持同一版本。断网保留最后已确认版本和时间，不把本地 AGENTS.md 自动写成云端人格。

人格变更按草稿、明确确认、发布三个状态推进。确认绑定具体内容哈希和版本；发布校验预期旧 revision，两个入口并发修改时返回冲突，不静默覆盖。普通记忆提取不应直接改已发布人格。

本地校验内容和版本后原子更新缓存，下一用户回合使用新版本。没有可验证缓存时使用产品默认规则，并说明尚未加载已确认人格。系统记录每回合实际使用的版本，不承诺离线设备实时一致。

### 4.5 观察与失败

记录以下观察字段：

- 记忆工具调用次数、服务端召回时间和网络等待。
- 首个非空文字时间、回合耗时和输入输出用量。
- 来源编号、人格 revision、待传数量和同步延迟。

记录不含原话、记忆正文、思考正文和令牌。失败与空结果分别表示。慢请求继续等待，可主动取消；首版不设置 800 毫秒或 2 秒的自动放弃规则。

未调用记忆工具的普通工作没有必经的云端查询。已经调用工具的回合仍可能等待网络，并增加模型处理工具结果的轮次；不承诺所有回合都更快或更省 token。工具明确失败或被取消后返回实际状态；依赖历史才能回答的问题应说明无法核实，不编造历史。

后台上传不作为回答前置条件，但仍占用本地磁盘和计算资源。按分批与单发送者策略控制资源，不把异步描述成零开销。

### 4.6 原话来源与记忆整理

原话库与 Hindsight 的索引分别存储。Hindsight 文档更新或索引重建不应覆写独立原话库。记忆引用可关联多条原话及修订，来源工具返回档案原文，不返回模型重述的内容作为原话。

截至 2026-10-13，官方文档说明相同 `document_id` 的默认 retain 会替换旧内容并重新处理，也提供 `update_mode: "append"`。Document API 可回读原文和文本片段；独立归档的原因是保留版本与历史，不是 Hindsight 完全不能保存原文。实现前按实际部署版本核对更新语义，不能把增量消息当作完整文档反复 replace。[Retain 文档](https://hindsight.vectorize.io/developer/api/retain)、[Documents 文档](https://hindsight.vectorize.io/developer/api/documents)。

原话逐条可靠归档，整理按有上下文的会话片段提取。写入 Hindsight 的片段带档案来源与覆盖范围，避免单独提取“可以”等依赖上文的消息。片段大小与更新方式在 N01 冻结，不强制每条消息立即提取。

信息来源、确认状态和有效时间分别记录。来源区分用户陈述、用户提问、助手回答和助手推断；确认状态表达未确认、用户明确确认、存在争议或已被替代。用户陈述证明用户说过该内容，不等于外部事实已经验证。

普通原话保存不要求逐条再次审批。问过方案不等于作出决定，助手推断不能自动升级为已确认个人资料。更正应保留新旧来源和替代关系；人格发布仍需明确确认。

首版不新增每轮自动检索层、独立 Reranker 或记忆编排 Agent。记录两类失败：模型需要历史却未调用工具，以及调用后未检索到正确资料。两类问题分别分析，不把按需调用视为检索质量已经解决。

### 7.1 工程门禁

以下命令按实际实现的触达范围运行。每次记录真实执行结果，不把计划中的命令算作已通过。

修 bug 先保留可复现的失败测试，再修正。新状态机、解析、幂等、队列和来源逻辑都有行为测试。测试文件在实现节点建立，不能预先执行不存在的测试并把它算成通过。

### 7.3 推进规则

1. 核对依赖和本节点边界。
2. 完成交付，运行对应验收。
3. 主负责人核对结果及证据。
4. 验收全满足时，更新节点记录并打勾，再进入下一项。
5. 失败或缺信息时，保留未完成状态和实际原因；只修本节点问题，不绕过验收。

### 7.4 必要测试与开发节奏

用户要求加快开发，并保留质量。节点仍按原顺序推进，测试按风险和触达范围选择，不以测试数量作为完成标准。

- 必测数据不丢、不重复、不串账号、原话逐字一致、归档不触发回答、问句和推断不变成决定，以及人格确认与版本冲突。优先用离线行为测试稳定覆盖。
