# 发布与日常观察

日期：2026-10-14。适用范围：已经提交的统一记忆实现。当前未部署、未启用日常配置；不得把源码提交当成安装版自动更新。

## 第一步：固定版本发布

由主负责人按已提交版本准备云端发布包与回退版本，执行发布预检。正式部署需用户授权。不得在服务器直接改源码。

先更新云端接口，再更新用户实际使用的 TPA 入口。核对云端 commit／契约版本和日常 TPA 的真实启动位置，避免只更新源码、仍启动旧安装版。部署只更新代码，不迁移未确认的旧资料；后台整理保持关闭，直到账号及写入门禁核对完成。

## 第二步：连接并启用

完成发布后，在实际日常 TPA 的设置页打开“云端记忆”。用户在该界面输入自己的云端账号凭据，无需把密码发到聊天。

核对账号、人格版本、连接状态，再启用云端记忆和个人／项目可见对话同步。按界面提示新建会话或重启运行时，确认新进程使用当前绑定。原话从启用后的新增消息开始归档，不上传全部旧历史。云端负责人核对当前账号 memory.auto 与提取、模型、Hindsight 写入门禁后，再启用后台整理。

原生同步状态尚未到达时保持“未知”。上传开始后，核对云端回执及待传状态，再确认已经同步；只看到连接成功不算消息已经归档。

## 第三步：正常使用至少三个使用日

用户继续日常聊天和项目工作，无需每天重做整套实验。遇到问题时，指出具体一轮的现象，例如：“这不是我的决定”“这条记忆已过时”“刚才没有必要查历史”“这次等待明显变长”。

主负责人根据记录检查以下问题：

- 需要历史时是否查到正确资料，引用是否能回看原话。
- 普通工作是否出现不必要的检索；记忆工具是否经常漏调用或选错。
- 两端使用的已确认人格与资料来源是否一致。
- 待传是否积压、失败是否可恢复，以及检索和后台整理的真实用量。
- 回答是否更了解用户，用户是否愿意保留这种行为。

先记录，再根据日常数据调整预算或调用提示；不先加新的速度门槛或每轮强制检索。

## 旧资料单独处理

旧正式 Hindsight 258 条无账号归属标签，当前迁移 0。新增链路启用不依赖先迁完旧资料。需要回补时，另选具体资料和 Pi 会话，先只读预览并确认归属，再小批次迁移；不通过放宽 owner 过滤一次性放行。

## 回退

桌面关闭云端记忆开关，并按界面提示新建会话或重启运行时；云端关闭后台提取门禁。保留原始会话、云端原件、待传队列及回执，必要时恢复已记录的旧代码版本。关闭本地等待不能撤回远端已经接受的写入。
